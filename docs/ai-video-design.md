# Part 4 Process and AI design

Before building recognition, I would spend time with employees in one aisle and record how they currently scan shelves. I would note how labels are positioned, where products obscure each other, how high shelves are reached, how quickly the camera moves, and when case counts are ambiguous. From those observations I would define a short capture procedure: start at a location marker, hold the camera steady, move across one shelf at a time, and finish at the next marker. A few example clips would show acceptable lighting, distance, and camera speed. The procedure should be tested with employees before it becomes a requirement.

The application would let an employee upload a video from a phone. It would store the original file privately, create a processing job, and show upload and processing status. A worker would extract representative frames, reduce near-duplicates and blur, and retain timestamps that link observations back to the video. Processing could happen after upload, so a weak warehouse connection would not require continuous streaming.

Location context is essential. I would place a readable location label or QR marker at each shelf boundary and require the clip to begin with it. The system would associate following frames with that location until the next marker. If a marker is absent or unclear, it would ask the employee to select the location; it would not infer a location from nearby products alone. The upload would also record the employee, scan time, and any manually selected aisle.

The recognition stage would identify candidate SKUs from packaging text, barcodes, and visual appearance, then count *visible full cases*. It would produce structured observations such as `{ sku, location, visible_case_count, confidence, frame_timestamps, evidence_images, model_version }`. A count of visible cases is an observation, not a claim about cases hidden behind other stock. Unmatched products and uncertain counts would be marked as unknown rather than forced to a plausible SKU.

I would evaluate with manually labeled clips from the pilot aisle, including different lighting, camera operators, package orientations, partially blocked cases, and mixed SKUs. Metrics would include correct location assignment, SKU precision and recall, exact case-count accuracy, and average absolute count error. I would also track the fraction of observations sent for human review and whether employees can correct them quickly. The test set should include difficult and ordinary footage; accuracy on polished demo clips alone would not justify using the system operationally.

Every proposed observation would enter a review queue. The employee would see the location, proposed SKU and count, confidence, and selected evidence frames, with controls to edit the SKU, adjust the count, mark an item unreadable, or reject the observation. Low-confidence results and any mismatch with existing inventory would require explicit review. An authorized reviewer would approve a batch before any inventory transaction could be created. The system would never directly overwrite a stock balance from raw AI output.

I would save the original video reference, extracted evidence, model output, confidence, employee corrections, approval identity and time, final decision, and any inventory transaction ID. This creates a history that can explain later discrepancies and supply labeled examples for evaluation. Retention and access rules would be defined before broad rollout.

The first prototype would use one aisle, a handful of visually distinct SKUs, and short clips with clear location markers. It would generate a review screen and measure recognition and count accuracy against manual counts. Only after that trial shows useful accuracy and a manageable review burden would I build full warehouse coverage or inventory updates.
